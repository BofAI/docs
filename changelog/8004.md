# 8004 Protocol

Release notes for the 8004 Protocol.

<div className="changelog-entry">
<div className="changelog-date">Sep 9, 2026</div>
<div className="changelog-body">

### Agent wallet and configuration corrections

<div className="changelog-tags"><span className="changelog-tag">Docs</span><span className="changelog-tag">Fix</span></div>

- **`setWallet()`** — four places showed four different call shapes. Each was valid on its own, but the inconsistency made the API look unstable, and the one-argument samples omitted the condition that makes them work. Every example now uses one shape per language (`setWallet(newWallet, options)` in TypeScript, `setWallet(new_wallet, chainId=None, *, new_wallet_signer=None, deadline=None, signature=None)` in Python), and the missing condition is spelled out: a bare `setWallet(address)` for a wallet *different from the owner* raises `New wallet must sign`. The SDK auto-signs only when the SDK signer already is the new wallet; otherwise you must pass `new_wallet_signer` / `newWalletSigner`, or a ready-made `signature` for smart contract wallets.
- **What the wallet signature actually covers** — a new *How the signature is supplied* section spells out the three signing paths and when each applies. The "what am I signing?" fields now carry the real constraints: `deadline` defaults to 60 seconds out and the contract caps it at **5 minutes**, the EIP-712 domain is `ERC8004IdentityRegistry` version `1`, and smart contract wallets are accepted through an [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271) `isValidSignature` fallback (previously only EOAs were described). `agentWallet` is also documented as a reserved key that `setMetadata()` and `register()` reject.
- **TRON `chainId`** — `chainId=1` is a legacy compatibility field and is no longer shown in any TRON initialization. Omitting it is what lets Nile produce the current `3448148188:<tokenId>` agent-ID form. EVM examples keep their real chain IDs.
- **TRON network names** — the network table and every example now use the bare names (`mainnet` / `nile` / `shasta`). Both SDKs still accept a `tron:`-prefixed alias such as `tron:nile` and strip the prefix internally, so existing code keeps working; note these are the SDK's own aliases, a different namespace from the CAIP-2 ids used by x402.
- **Registration file keys** — the hosted-file sample used `endpoints` and `x402support`. The registration-v1 wire format, which Python's `to_dict()` emits and the SDK's own fixtures carry, is `services` and `x402Support`; the sample was corrected to match. TypeScript is the exception — see the next entry.
- **Reading a loaded agent (TypeScript)** — the samples printed `loaded.registrationFile.name`, but `registrationFile` is `private readonly` on the `Agent` class, so that line does not compile. They now use the public `loaded.toJSON().name`. Python is unaffected: its `registration_file` attribute is public. Every complete TypeScript sample in the 8004 and x402 guides was type-checked against the published packages under `strict`.
- **Which release the docs describe** — the feature matrix now names the published npm release (`@bankofai/8004-sdk` 1.1.2) and notes that the Python package is not on PyPI. It also records a difference between the two languages: Python's `to_dict()` emits the registration-v1 wire keys (`services`, `x402Support`), while TypeScript publishes its internal names (`endpoints`, `x402support`), so a TypeScript caller must map them before hosting the file. The Python install commands now pin `main` (`git+…@main`, `git clone -b main`) — the repository's default branch is `develop`, so the unpinned form pulled unreleased code.
- **Where OASF slugs live** — the guide said skills and domains go in an `endpoints` array. Python builds an `OASF` entry inside `services`; TypeScript instead pushes the slugs into a flat top-level `tags` array and emits `tags` and `metadata` that Python's file does not carry. Both representations are now documented.
- **Private keys** — examples read from `TRON_PRIVATE_KEY` / `EVM_PRIVATE_KEY` environment variables instead of inline literals, and the samples that referenced undefined variables now run as written. A malformed 39-character example address was also corrected.
- **OASF skill and domain slugs** — the examples used two-level slugs (`technology/data_science`, `natural_language_processing/summarization`) that the taxonomy does not contain, several of them alongside `validate_oasf=True`, which raises. Every slug in the docs was re-checked by running the SDK's own `validate_skill()` / `validate_domain()` against the bundled taxonomy (136 skills, 204 domains); the invalid ones are now the three-level forms the taxonomy actually defines. The deliberately invalid `custom_skill/...` samples paired with `validate_oasf=False` were left alone. The OASF entry's own `version` in the registration-file sample was also wrong — `v0.8.0` where the SDK actually writes `0.8`, the value the 8004 spec example uses.
- **New: SDK Feature Matrix** — a single page listing what each language implementation actually supports, generated from the SDK source. It documents the previously undocumented Reputation, Validation, ownership/operator and discovery APIs, and records the parity gaps between them — most importantly that the **Validation Registry API exists only in TypeScript**.
